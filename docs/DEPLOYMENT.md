# Deployment Guide

Two deployment paths are supported. Pick one.

## Path A: Docker Compose (self-contained, any host with Docker)

```bash
cp .env.example .env
# fill in JWT_ACCESS_SECRET / JWT_REFRESH_SECRET (see .env.example for how to generate them)
docker compose up -d
```

That's the whole deployment: Postgres, Redis, migrations, seeding, backend, and frontend, all provisioned and wired together. Point a reverse proxy or load balancer at port 8080 (frontend) if deploying to a public host, and set `COOKIE_SECURE=true` once it's served over HTTPS.

## Path B: Free-tier hosted (Vercel + Render + Neon + Upstash)

No card required anywhere in this stack.

### 1. Neon (PostgreSQL)

1. Sign in at [neon.tech](https://neon.tech).
2. **New Project** → name it, pick a region, create.
3. Copy the connection string from **Dashboard → Connection Details**. It looks like:
   ```
   postgresql://user:password@ep-xxxx.region.aws.neon.tech/dbname?sslmode=require
   ```
   This single string is `DATABASE_URL`. Neon doesn't split pooled/direct connections the way some providers do.

### 2. Upstash (Redis)

1. Sign in at [console.upstash.com](https://console.upstash.com).
2. **Create Database** → Regional type, a region close to where the backend will run, create.
3. Open the database → **Details** tab → copy the **Redis Connection URL** (`rediss://default:<password>@<host>:<port>`, or sometimes shown as `redis://`). This is `REDIS_URL`. Either way, also set `REDIS_TLS=true`: Upstash requires a TLS handshake regardless of which scheme the copied string uses, and this can't be reliably inferred from the URL alone.

### 3. Render (backend)

1. Sign in at [render.com](https://render.com) with GitHub.
2. **New → Blueprint**, select the `callvitals-pro` repo. Render reads `render.yaml` at the repo root and proposes a `callvitals-pro-backend` web service built from `backend/Dockerfile`.
3. Before the first deploy, fill in the env vars marked `sync: false` in `render.yaml`:
   - `DATABASE_URL`: the Neon connection string
   - `REDIS_URL`: the Upstash connection string
   - `CORS_ORIGIN`: the frontend's Vercel URL (you won't have this until step 4; a placeholder works for the first deploy, update it after)
   - `SEED_ADMIN_PASSWORD` / `SEED_ANALYST_PASSWORD`: choose real passwords, don't ship the repo's defaults
4. Deploy. `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` are auto-generated by Render (`generateValue: true`) and `COOKIE_SECURE` is already `true`.
5. Once live, note the service's URL (`https://callvitals-pro-backend.onrender.com`). Confirm it's up:
   ```bash
   curl https://callvitals-pro-backend.onrender.com/health
   ```

Render's free tier spins the service down after 15 minutes of no traffic; the next request wakes it up, which takes roughly 30 seconds. This is a free-tier tradeoff, not a bug.

### 4. Vercel (frontend)

1. Sign in at [vercel.com](https://vercel.com).
2. **Add New → Project**, import the `callvitals-pro` repo.
3. Set **Root Directory** to `frontend`.
4. Add an environment variable: `VITE_API_BASE_URL` = `https://callvitals-pro-backend.onrender.com/api` (the Render URL from step 3, with `/api`).
5. Deploy. Vercel auto-detects the Vite build (`npm run build`, output `dist`).
6. Copy the deployed URL and go back to Render to set `CORS_ORIGIN` to this exact origin (no trailing slash), then redeploy the backend so the new value takes effect.

### 5. Verify

```bash
curl https://<your-vercel-app>.vercel.app
curl -X POST https://callvitals-pro-backend.onrender.com/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@callvitals.dev","password":"<your SEED_ADMIN_PASSWORD>"}'
```

Then open the Vercel URL in a browser and sign in with the same credentials.

## Common pitfalls

- **CORS errors in the browser console**: `CORS_ORIGIN` on the backend must exactly match the frontend's origin (scheme + host, no trailing slash, no path).
- **Login works but refresh/logout silently fail across domains**: `COOKIE_SECURE` must be `true` on the backend whenever frontend and backend are on different domains, since that's what switches the refresh cookie to `SameSite=None` (required for cross-site cookies) instead of `Lax`.
- **First request after idle is slow**: expected on Render's free tier (cold start), not an application bug.
